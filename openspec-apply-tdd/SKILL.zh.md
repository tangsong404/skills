# OpenSpec 应用与 TDD

将 OpenSpec 变更执行与测试驱动开发相集成。对于 OpenSpec 变更中的每个任务，使用红-绿-重构循环而非直接编写代码。

## 两种方法的结合

| OpenSpec 阶段 | TDD 阶段 |
|---|---|
| 选择变更，阅读上下文 | **规划**：理解需求，识别行为 |
| 识别待办任务 | **分解**：将任务分解为可观察的行为 |
| — | **红**：为第一个行为编写一个测试 |
| — | **绿**：编写最少代码使其通过 |
| — | **重构**：深化模块，清理代码 |
| 标记任务完成 | 对每个行为重复红-绿-重构 |
| 下一任务 | 继续 TDD 循环 |

## 工作流程

### 1. 选择变更

如果提供了名称，则使用该名称。否则从对话上下文中推断，或使用 `openspec list --json` 让用户选择。

宣布："正在使用变更：<名称>"

### 2. 检查状态

```bash
openspec status --change "<名称>" --json
```

解析 JSON 以了解所使用的 schema 以及哪个工件包含任务。

### 3. 获取应用指令

```bash
openspec instructions apply --change "<名称>" --json
```

阅读 `contextFiles` 下列出的所有上下文文件。在规划之前理解变更的内容。

**处理状态：**
- `blocked`：显示消息，建议更新工件
- `all_done`：祝贺完成，建议归档
- 其他状态：继续执行 TDD 实施

### 4. TDD 实施循环（每个任务）

对于每个待办任务，**不要先编写所有代码**。而是将任务分解为单个可观察的行为，并通过红-绿-重构逐一实现。

#### 每个行为周期

```
┌─────────────────────────────────┐
│  规划："这个任务需要什么行为？    │
│  公共接口是什么？"               │
└──────────┬──────────────────────┘
           ▼
┌─────────────────────────────────┐
│  红：为此行为编写一个测试        │
│  → 测试失败                      │
│  （测试描述"什么"，而非"如何"）   │
└──────────┬──────────────────────┘
           ▼
┌─────────────────────────────────┐
│  绿：编写最少代码使其通过此测试   │
│  （不要推测未来的测试）           │
└──────────┬──────────────────────┘
           ▼
┌─────────────────────────────────┐
│  重构：在测试保持绿色的前提下      │
│  清理代码                        │
│  （深化模块，提取重复代码，        │
│   绝不在红色状态下重构）           │
└──────────┬──────────────────────┘
           ▼
    ┌──────────────┐
    │ 还有更多行为？ │
    ├───────┬────────┘
    │ 是    │ 否
    ▼       ▼
  重复     任务完成 →
           标记 `- [x]` 到任务列表
           继续下一任务
```

**每个周期的规则：**
- 一次只写一个测试 — 不批量处理
- 只编写足以通过当前测试的代码 — 不添加推测性功能
- 测试通过公共接口描述可观察行为 — 不测试实现细节
- 绝不在红色状态下重构 — 先让测试变绿
- 每次重构步骤后运行测试

#### 规划阶段详情

在任务的第一个红测试之前，与用户确认：
1. 公共接口应该是什么样子
2. 首先测试哪些行为（优先考虑关键路径和复杂逻辑）
3. 识别深度模块的机会（小接口，深实现）
4. 为可测试性设计接口：接受依赖，返回结果

#### 测试质量指南

编写**集成风格测试**，通过公共 API 执行真实代码路径：
- 测试系统**做什么**，而不是它**如何做**
- 测试通过意味着行为工作正常，而不是内部方法被调用
- 测试应能经受内部重构

**仅在系统边界使用模拟**：外部 API、数据库（有时更倾向测试数据库）、时间/随机性、文件系统。切勿模拟自己的模块或内部协作者。

参考文件获取更深入的指导：
- `references/tests.md` — 好测试与坏测试示例
- `references/mocking.md` — 何时以及如何模拟
- `references/deep-modules.md` — 设计小接口深实现的模块
- `references/interface-design.md` — 为可测试性设计接口
- `references/refactoring.md` — 测试变绿后的重构候选

#### 每个任务的完成

当一个任务的所有行为都实现后：
1. 运行完整的测试套件 — 所有测试应通过
2. 更新任务复选框：`- [ ]` → `- [x]`
3. 显示已实现内容的摘要
4. 继续下一任务

### 5. 完成或暂停

**完成：**
```
## 实施完成

**变更：** <变更名称>
**Schema：** <schema名称>
**进度：** 7/7 任务完成 ✓

所有任务已完成！可以归档此变更。
```

**暂停（遇到问题）：**
```
## 实施暂停

**变更：** <变更名称>
**进度：** 4/7 任务完成

### 问题
<描述>

### 选项
1. <选项 1>
2. <选项 2>
3. 其他方法

你想怎么做？
```

### 保护措施

- 将每个 OpenSpec 任务分解为行为 — 不要一次性完成所有工作
- 每个行为一个红-绿-重构循环 — 这是 TDD 的核心纪律
- 在规划实施内容之前，始终先阅读上下文文件
- 如果任务不明确，暂停并在开始红色阶段之前提问
- 如果实施过程中发现设计问题，建议更新工件
- 保持代码变更聚焦于通过当前测试 — 不添加推测性范围
- 遇到错误或阻塞时，报告并等待指导
